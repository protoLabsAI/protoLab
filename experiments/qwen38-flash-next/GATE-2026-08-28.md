# Qwen3.8-Flash-Next — due diligence, 2026-08-28

**Verdict: DO NOT ADOPT YET. Not a tuning decision — it does not run on any released vLLM.**
Re-gate when the conditions at the bottom are met. No download, no quant, no lane.

## What it is

[`Qwen/Qwen3.8-Flash-Next`](https://huggingface.co/Qwen/Qwen3.8-Flash-Next), released
**2026-08-24** (4 days ago). Marketed as an early preview of the **Qwen4 architecture**,
with a production `Qwen3.8-Flash` to follow on QwenCloud at $0.16/$0.47 per 1M in/out.

```
architectures     Qwen4ExpForConditionalGeneration     <- NEW ARCH, not qwen3_5
model_type        qwen4_exp
params            125B backbone (6B active) + 51B N-gram table + 4B MTP
layers            48, hybrid linear_attention : full_attention = 3:1
MoE               512 experts, 10 active, moe_intermediate_size 640 (fine-grained)
attention         24 heads / 2 KV heads, head_dim 256, partial rotary
context           262144 native, ~1M with YaRN
multimodal        yes (vision_config, image + video tokens)
MTP               mtp_num_hidden_layers 1, dedicated embeddings
```

Novel components, none of which exist in our stack today: **N-gram embeddings**
(`ngram_size 3`, `heads_per_ngram 8`), **per-layer embeddings / PLE** (`ple_embed_dim`,
`ple_layer_ids`), **hyper-connections** (`hc_count 4`, `hc_lowrank 320`), and a **sparse
attention indexer** (`indexer_budget 2048`, `indexer_compress_ratio 4`) — the same family
as DeepSeek-V4's DSA, which cost us a whole forked build last time.

The hybrid linear/full attention split *is* familiar — same GDN-hybrid family as our
Qwen3.8-27B lane — so that part of our operating knowledge would carry.

## Blocker 1: no released vLLM supports it

```
vLLM v0.28.0 (latest stable, 2026-08-26)   no qwen4* model file, no qwen4_exp in registry
vLLM main                                  no qwen4_exp
vLLM 0.25.1 (what we run)                  no qwen4_exp
```

Support is **five open, unmerged PRs**, all filed in the last 48 hours:

```
#53896  OPEN  [Model] Support Qwen3.8-Flash-Next          <- the core one
#53909  OPEN  [Kernel][Qwen] Add qwen4 fuse op
#53899  OPEN  Support PLE-Offload for Qwen3.8-Flash-Next  }
#54070  OPEN  [Feature] Disk-backed PLE n-gram tables     } three competing PLE designs
#54129  OPEN  [Model] Support disk-backed (mmap) PLE      }
```

Three competing implementations of PLE offload means the memory story is **not settled
upstream**. Whatever we built against today would likely need rework.

## Blocker 2: it does not fit, and the quants that do take both cards

```
artifact                                   size      verdict
Qwen/Qwen3.8-Flash-Next          bf16     360.0 GB   impossible (192 GB total VRAM)
Qwen/Qwen3.8-Flash-Next-FP8              185.6 GB   ~6 GB left for KV+activations across
                                                     both cards. Not serveable.
RadixArk/...-NVFP4                       135.3 GB   TP=2 only, ~68 GB/card
Inferact/...-NVFP4                       182.8 GB   barely quantized, not viable
```

Even the viable NVFP4 needs **TP=2 across both cards**, which means:
- it **replaces the entire smart replica pair** — we would be back to one model, one lane,
  after deliberately moving to replicas on 2026-08-23;
- TP=2 on this PCIe box is our known-weak configuration (replicas beat TP=2; that finding
  predates this repo's current fleet).

Storage is also tight: `/mnt/models` has **113 GB free**, so a 135 GB NVFP4 does not fit
there at all. It would have to go to `/mnt/data` (303 GB free).

## Blocker 3: an open crash on our GPU class, in the path we just validated

[vllm#54173](https://github.com/vllm-project/vllm/issues/54173), opened **today**:
`CUBLAS_STATUS_INTERNAL_ERROR` then `illegal memory access` in the **GDN path** on
Blackwell, with the RadixArk NVFP4 checkpoint. Trigger is **prefix caching with growing
multi-turn prefixes** — identical repeated prompts are fine, differing lengths sharing a
prefix crash it. Workaround is `--no-enable-prefix-caching`, i.e. full re-prefill every
turn. Reporter notes it is distinct from #50021 and persists with `--no-async-scheduling`.

Worth sitting with: we spent today establishing that *our* GDN + prefix-caching +
spec-decode stack is clean across all 128 residues. This model's GDN path on Blackwell is
not, yet — and prefix caching is load-bearing for our agentic traffic.

## The genuinely interesting idea, and the thing to watch

Qwen's own framing of N-gram embeddings, from the model card:

> Embeddings provide a unique axis for parameter scaling that requires less computation
> and is **more amenable to offloading than Mixture-of-Experts**. By indexing with short
> n-grams, this approach makes parameter scaling highly efficient **for memory-constrained
> accelerators** without sacrificing quality.

That is the whole bet: 51B of the parameter count is a lookup table, not compute, so it
can live off the GPU. If one of the three PLE-offload PRs lands, resident VRAM could drop
well below the 135 GB disk figure and the TP=2/both-cards objection may evaporate. **That
is the specific thing that would change this verdict**, and it is worth tracking rather
than the headline benchmark scores.

## Re-gate conditions

Revisit when **all** of these hold — not before:

1. `#53896` merged and shipped in a tagged vLLM release (realistically >= v0.29.0).
2. A PLE-offload PR merged, with a measured resident-VRAM number for NVFP4. If that number
   is <= ~85 GB it becomes a single-card lane and the calculus changes completely.
3. `#54173` closed, or confirmed not to reproduce on sm120 with prefix caching ON.

Then, and only then: pull the NVFP4 to `/mnt/data`, stand it up on ONE card if offload
allows it, and gate it with `eval-model.sh` against the current smart lane. Do not evaluate
it TP=2 against a replica pair — that comparison is rigged against us before it starts.

## Also seen while looking

**GLM-5.3-Flash** is having a parallel bad time on our exact GPU class:
[#54150](https://github.com/vllm-project/vllm/issues/54150) (ModelOpt NVFP4 emits invalid
UTF-8 byte tokens on SM12x) and [#54059](https://github.com/vllm-project/vllm/issues/54059)
(no sparse-MLA path on Ada). Both are the same lesson we keep re-learning: **new
architecture + NVFP4 + SM12x is where the bodies are**, and being early costs more than
the model is worth until the kernels settle.

Also [#54122](https://github.com/vllm-project/vllm/issues/54122): cold AOT compilation is
charged as peak activation memory, shrinking the KV pool. That one is worth reading for
our own lanes regardless of this model.

# Addendum — 2026-08-31

Two things happened since the gate was written. The verdict holds; the *reasons*
changed enough that the original Blocker 2 is now wrong as stated.

## 1. A working single-card deployment exists — on SGLang, not vLLM

[`jpezzulli/sglang-rtxpro6000`](https://github.com/jpezzulli/sglang-rtxpro6000)
("Pennyroyal v2.1.1", Apache-2.0, `sglang==0.5.19.dev490`) serves
`RadixArk/Qwen3.8-Flash-Next-NVFP4` on **one** RTX PRO 6000 at TP=1, 524K YaRN,
824,384-token KV pool, 450 W cap. Measured there vs our own smart lane,
measured the same day at C1/C4 on coherent prompts with thinking off:

```
                                    C1 decode    C4 aggregate   cold prefill 64K
Flash-Next NVFP4, their fork, 1 card    171.1        427.5           10,104 tok/s
their Qwen3.8-27B FP8 + DFlash2         108.9        375.8            6,169 tok/s
OUR Qwen3.8-27B NVFP4 + MTP K=3 :8041    88.7        329.9            —
```

**How it fits, and why that does not help us.** The checkpoint splits
`plefp8` 51.2 GB / everything else 84.1 GB. Their launcher passes
`--ple-offload-embedding`; `Qwen4ExpPinnedHostEmbedding` allocates the 51.2 GB
n-gram table `device="cpu", pin_memory=True` and gathers it per token by a
Triton kernel over PCIe. So ~84 GB stays resident and the card fits it.

The trade is **VRAM for pinned host RAM**, and host RAM is this box's scarcest
resource: 61 GB total, ~40 available, and pinned pages do not swap. Their config
also wants a 32 GB HiCache host tier on top. Same constraint already recorded in
[[reference_comfyui_host_ram_highvram]]. Concretely fixable — `dmidecode` shows
**2x 32 GB DDR5 with two slots empty**, so 128 GB is a DIMM purchase, not a
rebuild.

Also in their `RESULTS.md`: a third party ran the FP8 checkpoint TP=2/EP=2 on
**exactly our hardware** (dual RTX PRO 6000, no NVLink) — 200.9 tok/s C1 to
339.3 at C6, 3.18M-token KV pool. What made MTP boot was dropping
`SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1`; an earlier graph-capture failure was
cured by removing `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, which we
set on several lanes.

## 2. vllm#53896 merged — and the merge does less than it sounds like

Merged `2026-08-31T05:57:56Z`, five days after `v0.28.0` was cut, so no
installable release carries it. Reading the merged tree matters more than the
merge:

- **No PLE offload landed.** `vllm/models/qwen4_exp/nvidia/ple_layer.py` and
  `common/ple.py` keep the table fully device-resident — no `pin_memory`, no
  `mmap`, no CPU placement. A release carrying #53896 alone still means 135.3 GB
  resident, TP=2 only, ~68 GB/card, which kills the smart replica pair.
  **Condition 1 alone buys nothing we want; condition 2 is load-bearing.**
- **NEW CONSTRAINT — the merged path forbids fp8 KV.** `nvidia/qsa.py` raises
  `NotImplementedError("Qwen4Exp QSA requires a BF16 main KV cache")` and
  `("Qwen4Exp QSA does not support KV quantization")`. Every lane in our fleet
  runs `--kv-cache-dtype fp8`. The SGLang fork serves this model with FP8 E4M3
  KV, so **upstream vLLM is currently the more restrictive runtime**. Any
  re-gate must budget bf16 KV.
- **sm120 is acknowledged, as a de-optimization not a gate.**
  `nvidia/ops/qsa.py:791` excludes capability-family 120 from `cooperative_topk`
  and falls back to `persistent_topk`. Not a blocker.
- **No sm120 CI.** `tests/evals/qwen4_exp/configs/` ships `models-b200.txt` and
  `models-h200.txt` only, against the FP8 checkpoint — no NVFP4 accuracy config
  upstream.

Correction to the original doc: **#54173 is filed against GB10 / sm_121**, not
our sm_120. It may not apply to us at all.

## Re-gate conditions — revised

Condition 2 as originally written ("resident VRAM <= ~85 GB makes it a
single-card lane") is now **demonstrated to be achievable** — just not in vLLM,
and not within our host RAM. Restated:

1. `#53896` in a tagged release (>= v0.29.0). **Necessary, not interesting on
   its own** — see above.
2. A PLE-offload PR merged **with a measured NVFP4 resident-VRAM number**.
   Three competing designs are open: `#53899` (pinned host), `#54129` (mmap),
   `#54070` (disk-backed). **Whichever merges first satisfies this.** The mmap
   variant is the one that does *not* need 51 GB of pinned host RAM.
3. `#54173` closed, or confirmed not to reproduce on sm_120 with prefix caching
   ON.
4. **NEW:** a KV budget that assumes **bf16, not fp8**, until upstream lifts the
   QSA restriction.

Host RAM (128 GB) is a precondition only for the *pinned* offload design, not
the mmap one.
