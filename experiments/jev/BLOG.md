# Everyone is cloning Jev. Nobody is measuring the part that matters.

> Code and aggregate results: [`experiments/jev/`](https://github.com/protoLabsAI/lab/tree/main/experiments/jev).
> Per-item probability files are regenerated by `prep_data.py` + `run_all.sh` (the repo does not
> track `.jsonl`); every number below then falls out of `python metrics.py`, `bootstrap.py` and
> `defer.py`, whose full outputs are committed under `results/`.
>
> **No cloud calls were made. Jev itself is not measured here** — this is the local baseline a Jev
> comparison has to beat, and it turned out to be more interesting than the comparison would
> have been.

TypeSafe shipped [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) on
2026-09-15: a "System One" model that takes unstructured text plus a typed question and returns a
typed value with a calibrated probability, in one forward pass, no chain of thought. Three
primitives — `choice`, `score`, `noul` (boolean-with-probability). No strings, no JSON to parse.

Within five days there were two MIT-licensed open replicas
([OpenJev](https://github.com/GitHub30/OpenJev),
[system-one-open](https://github.com/mithalouni/system-one-open)), and the pattern was all over
my feed. OpenJev's recipe is: take any HF instruct model, score the candidate options'
loglikelihoods in one forward pass, softmax, optionally fit a temperature. It reports no
benchmarks. That is not a criticism of the repo — it is a three-day-old wrapper and it is honest
about it — but it means an entire pattern is being adopted on vibes.

I had already built the local side of that comparison. Here is what the numbers say.

---

## The question is not "can a small model do constrained output"

We have had constrained decoding for a long time: xgrammar on the vLLM lanes, GBNF in llama.cpp.
Jev's "0% hallucination" is definitional and TypeSafe says so — "schema matching is guaranteed."
A grammar gives you the same guarantee. It tells you nothing about whether the chosen option is
*right*.

The interesting claim is **calibration**: a probability you can put a threshold on. And the
reason that matters is not that the number is pretty. It is that a decision model earns its
place by **knowing when to hand off to a big model**. So:

> Can a tiny local model doing grammar-constrained single-token decoding, plus post-hoc
> calibration, match a purpose-trained decision model on *deferral quality* — not accuracy?

Accuracy cannot answer that. Risk-coverage can.

## Setup

Four suites, chosen to mirror Jev's own demos so the comparison is on their home turf:
`injection` (2-way, deepset/prompt-injections), `sentiment` (2, SST-2 validation), `routing`
(11 support queues, bitext), `langid` (20 languages). Disjoint seeded splits — `test` (300,
scored), `calib` (200, fits temperature only, never scored), `train` (embed-head only).

Arms, all local, all one forward pass:

```
arm            what
embed-head     Qwen3-Embedding-0.6B + a softmax head        sees labels
tiny-grammar   Qwen3.5-0.8B / 2B / 4B on CPU, max_tokens=1  zero-shot
smart-lane     Qwen3.8-27B-NVFP4 on :8041, same constraint  zero-shot, the upper bound
```

The readout: `max_tokens=1`, thinking off, restrict the next-token distribution to each option's
first token, renormalise. First tokens are unique in every suite (asserted in code), so under a
grammar permitting only the option strings, P(first token) **is** P(option). This is not an
approximation of constrained decoding — it is constrained decoding, with the grammar's effect
computed in closed form.

## Finding 1: the answer format costs more than the model size

Same model, same items, only the answer format changes — MMLU-style `A) B) C)` versus emitting
the option text itself:

```
model          suite     letter    name
Qwen3.5-2B     langid     0.100   0.503
Qwen3.5-4B     langid     0.570   0.953
Qwen3.5-2B     routing    0.367   0.637
smart 27B      langid     0.873   0.993
```

Free generation confirms it is the model, not the harness: the 2B answers "B" (Bulgarian) for
Polish *and* Spanish text. It knows the language. It cannot do the language→letter indirection
across 20 options. A 4B on langid goes from 0.570 to 0.953 — larger than the 2B→4B step — purely
by letting it say "Polish".

Jev's API shape makes this mistake impossible: you hand it criteria, it hands you one of them.
That design choice is worth more than it looks.

## Finding 2: post-hoc calibration does not transfer across tasks

`T-in` = temperature fitted on the same task's calib split. `T-loso` = fitted on the *other
three* tasks — the honest proxy for "calibrated on a task it has never seen", which is what a
general decision model must do.

```
condition                   better   WORSE   n.s.     (20 cells, 95% paired bootstrap)
T-in   (same-task labels)        9       1     10
T-loso (transferred)             6       5      9
```

Transfer is a coin flip, and where it loses it loses badly: the 0.8B's routing ECE goes
0.108 → 0.374. The mechanism is visible in the fitted temperatures — **tasks disagree about
which direction is wrong**. The 27B is *under*-confident on injection (T=0.43, needs sharpening)
and *over*-confident on routing (T=1.78, needs softening). No global scalar fixes both.

That is exactly the gap TypeSafe claims RLCD closes, and it is the first thing I would test
against the real thing.

## Finding 3: calibration is a trap metric on its own

`Qwen3.5-2B` on langid, letter format, after temperature scaling: **ECE 0.006**. Near-perfectly
calibrated. At **10% accuracy** — it gets there by flattening to near-uniform (T=8.76).

If you report ECE without deferral you will ship this model.

## The part nobody is measuring

Which brings us to risk-coverage. Sort items by the model's confidence, answer the top C%, and
measure accuracy on what you kept. AURC is the mean error across all coverages; lower is better.

```
arm                suite       acc   sel@95  sel@90  sel@80  sel@50    AURC [95% CI]
smart 27B          langid     0.993   1.000   1.000   1.000   1.000   0.000 [0.000,0.000]
smart 27B          routing    0.803   0.818   0.830   0.858   0.887   0.107 [0.072,0.151]
Qwen3.5-4B         sentiment  0.947   0.961   0.967   0.979   1.000   0.010 [0.004,0.017]
Qwen3.5-4B         langid     0.953   0.965   0.970   0.979   0.993   0.011 [0.003,0.021]
Qwen3.5-2B-letter  langid     0.100   0.091   0.081   0.079   0.080   0.921 [0.879,0.957]
```

The 27B's langid confidence is not merely good, it is perfect: both of its two errors in 300 are
items it flagged as its least confident. And the 4B *out-ranks its own accuracy* — 0.947 on
sentiment but 1.000 on its confident half.

Then there is the ECE-0.006 model from Finding 3. Its selective accuracy at 50% coverage is
**0.080**, *below* its 0.100 overall accuracy. Its confidence is anti-correlated with
correctness. Deferring its least-confident half makes the kept half **worse**. Perfectly
calibrated, actively harmful as a router.

## Finding 4: temperature scaling cannot change a binary decision's deferral, ever

Every two-option cell in my `ΔAURC` table came back exactly `+0.0000 [+0.0000, +0.0000]`. That
is not a weak null — it is an identity I should have seen coming.

For two options, the confidence is

```
max softmax = σ( |z₁ − z₂| / T )
```

which is monotone increasing in `|z₁ − z₂|` for every `T > 0`. Temperature rescales the
probability axis. It **cannot reorder items**. So AURC, and selective accuracy at any fixed
coverage, are invariant to temperature on any binary decision.

**Read that against Jev's `noul` primitive, and against every open replica whose calibration
story is "we fit a temperature".** On a boolean decision, that step moves ECE and Brier and
cannot change which items a rank-based router hands off. It is not worthless — it tells you
*which probability value* corresponds to a given coverage, which is how you pick a threshold
offline. But the quality of the frontier is fixed at decode time. If someone claims calibration
improved their binary routing, the mechanism has to be something other than temperature.

Where temperature *can* reorder (`k > 2`, 16 cells), it is 5 better / 5 worse / 6 not
significant. A coin flip.

## The headline I had after four tasks — and what happened when I widened it

Every arm answered the same id-aligned test items, so the cascade can be simulated exactly rather
than estimated. The small model answers what it is confident about; the rest go to the 27B lane.
`defer%` is the share of items that cost a 27B call. Pooled over four suites, paired bootstrap
resampled within suite:

```
arm                defer%   pooled acc   Δ vs 27B alone          verdict
smart 27B alone      100%        0.912   —
Qwen3.5-4B             0%        0.866   −0.046 [−0.065,−0.027]  worse
Qwen3.5-4B            10%        0.887   −0.024 [−0.040,−0.008]  worse
Qwen3.5-4B            20%        0.904   −0.007 [−0.021,+0.006]  n.s.
Qwen3.5-4B            30%        0.917   +0.004 [−0.007,+0.015]  n.s.
embed-head 0.6B       50%        0.938   +0.026 [+0.014,+0.038]  beats 27B
```

On those four tasks, a 4B deferring its least-confident fifth lands within noise of the frontier
lane. Eighty percent of the decisions, apparently, not needing a 27B.

**Then I widened the benchmark to 22 tasks across six families, and the result evaporated.**

```
                          4 tasks                       22 tasks
4B alone            0.866  -0.046 [-0.065,-0.027]   0.722  -0.059 [-0.069,-0.050]
4B + defer 20%      0.904  -0.007 [-0.021,+0.006]   0.758  -0.024 [-0.032,-0.016]
4B + defer 30%      0.917  +0.004 [-0.007,+0.015]   0.768  -0.014 [-0.020,-0.007]
4B + defer 50%      0.915  +0.003 [-0.003,+0.009]   0.778  -0.004 [-0.008,-0.000]
```

At 22 tasks **every** deferral rate is significantly worse than the 27B alone — including
deferring half the traffic. The parity claim was true of those four tasks and does not
generalise.

It was not a statistical fluke. The per-item bootstrap was honest and tight. It was a **task
sample** fluke: my four tasks happened to include language ID, where a 4B scores 0.953 against
the 27B's 0.993, and binary sentiment at 0.947 vs 0.957. The nineteen I added are less kind —
ordinal 0.519 vs 0.602, NLI 0.799 vs 0.861, safety 0.736 vs 0.778.

I keep a standing rule in this lab that an underpowered experiment is not a null result. This is
that rule biting from the other side: four tasks did not fail to detect an effect, they
*manufactured* one. Task-level *n* governs a task-level claim no matter how tight the per-item
intervals look.

**What actually survives, at its real size:** deferring the 4B's least-confident 20% closes
**60% of the gap** to the 27B while paying for 20% of the 27B calls; 50% deferral closes 93%.
That is a genuine cost lever. It is not parity, and I should not have implied it was on four
tasks.

The budget is strongly per-task — on the original four, the smallest deferral rate reaching
27B-alone accuracy was:

```
arm              injection  sentiment  routing  langid
Qwen3.5-4B             19%        11%      31%     35%
embed-head 0.6B         2%        47%       0%     56%
Qwen3.5-0.8B           69%        70%      47%   never
```

There is no universal "how much can the small model take". It is a property of the task, and 200
labelled calib items are enough to measure it.

### The threshold is deployable, not an oracle

Deferring a fixed *fraction* of test items quietly uses the test set to locate the cut. So I
refit: pick one confidence threshold on the calib split, apply it unchanged to test, live with
whatever coverage it yields. For the 4B, accuracy matches the oracle version to within ±0.010 in
every cell and exactly 0.000 in 7 of 12.

What does *not* transfer cleanly is the **budget**: asking for 30% deferral bought 27% on
injection and 37% on langid. Plan the cost envelope with slack. The accuracy is the stable part;
the spend is not.

## And then, with labels, the boring thing wins

A 0.6B embedder with a softmax head on a few hundred labels beats the 27B zero-shot on routing,
**0.960 vs 0.803**, with an AURC of 0.002. Support-queue categories are dataset conventions, and
conventions cannot be guessed — only learned. At 50% deferral that same head is the only arm here
that significantly *beats* the 27B pooled.

If you have labels, a zero-shot decision model has to justify itself on "no labels needed",
not on quality.

## What this means for the open-Jev wave

OpenJev's inference path *is* the tiny-grammar arm above. Its calibration step *is* `T-in`. So:

1. The temperature step is a **no-op for the ordering** of any `noul` decision (Finding 4).
2. It does **not transfer** across task families (Finding 2), which is the whole premise of a
   general decision model.
3. The thing that actually buys frontier-grade quality is the **deferral budget** (the headline),
   which neither open repo measures and which TypeSafe's marketing does not mention either.

`system-one-open` does report 74.8% on held-out task types, which as far as I can tell is the
first public cross-domain number for this model class, and is the right thing to compare against
once there is a shared eval.

None of this says Jev is bad. It says the open replicas are cloning the cheap half. The
expensive half is whatever RLCD does to make calibration survive a task the model has never
seen — and that is precisely the cell where my post-hoc temperature fails.

## So which half is hard? (I went and checked)

The obvious follow-up: if post-hoc temperature is the cheap half and RLCD is the expensive one,
how much is actually *in* the expensive half? That question turns out to be answerable with no
new inference at all.

Fit isotonic regression **on the test set itself** — an oracle, deliberately, not a method. That
is the best any monotone recalibration could ever do. The gap between raw and oracle is the
entire scale budget; whatever is left is ranking, and ranking is a training lever.

```
arms                              Brier   oracle floor   scale budget
27B + 4B (the deployable ones)    0.086          0.072   0.013 (16%)
0.8B / 2B-letter / embed-head     0.265          0.119   0.146 (55%)
```

**A perfect calibrator buys the 27B 0.010 Brier.** Five-sixths of its error is in the floor. And
the arms with a big scale budget are precisely the broken ones — the 0.8B below the capability
floor, the flattened 2B-letter, the under-confident embedder. A large calibration budget is a
symptom, not an opportunity.

I also tried the cheap shortcut properly: `log T = w · [entropy, margin, label_mass, log k, log
len]` — decode-time features only — fitted on three suites and applied to a fourth it had never
seen. A per-item temperature *can* reorder items, so unlike a global scalar it gets a shot at
both halves. Over 32 cells it was 10 better / 7 worse on ECE versus a global temperature, and
**net negative on AURC** (6 better / 9 worse). The split is systematic: it rescues broken arms
(2B-letter langid −0.453 ECE) and damages good ones (27B langid +0.104). Those features detect an
arm that has stopped working. They carry nothing about the fine structure that separates a good
arm from a calibrated one.

So the cheap path is closed, and the answer is the inconvenient one: **for a working decision arm
the hard half is ranking, and ranking only moves with training.** Which is exactly what the
binary identity in Finding 4 predicted, now with a number on it.

One consolation prize, and it is a good one: on arms where *both* readout formats are individually
competent, averaging the two distributions is the cheapest deferral improvement I found. The 27B's
AURC on routing — its worst suite — goes 0.1075 → 0.0830, −23%, for one extra forward pass and no
training. On the 4B it is worse everywhere, because its `letter` view is the broken one from
Finding 1. **Averaging with a broken view poisons the signal.**

## Three more things the wider set changed

**Calibration transfer is not a coin flip — that was a data-volume artifact.** On four tasks, a
temperature fitted on three and applied to the fourth was 6 better / 5 worse / 9 n.s., and I
called it a coin flip. Fitted on 21 tasks across five families and applied to a held-out sixth:
**26 better / 14 worse / 8 n.s.** Twice as often better as worse. It is a weak effect that three
tasks cannot estimate, not an absent one. It still doesn't rescue post-hoc calibration — the
oracle ceiling caps it at ~11–27% of Brier on a working arm, and on binary decisions it still
can't touch ranking at all — but "weak but real" is the honest phrasing, and I had the wrong one.

**The `score` primitive is the hardest thing here, and nobody has measured it.** The family v0
never tested is the one every arm is worst at. Star ratings put the *27B* at 0.602 accuracy with
AURC 0.270 — its confidence barely ranks its own errors — and ordinal carries the largest
absolute scale budget of any family, twice the next. That makes sense: adjacent-class errors are
graded, and probability spread across neighbouring stars is informative rather than
miscalibrated. If a Jev comparison is ever run, ordinal is the sharpest cell, and it is the
primitive with zero public numbers.

**A verifier helps exactly when it is more accurate than the decider.** Finding 12 held across
22 tasks and turned into a rule with no exceptions in this data:

```
verifier          family     verifier acc   4B acc    AURC self -> verifier   verdict
embed-head 0.6B   safety            0.813    0.736       0.1531    0.0967     better
embed-head 0.6B   topic             0.812    0.748       0.1198    0.0743     better
embed-head 0.6B   sentiment         0.694    0.676       0.2078    0.1609     better
embed-head 0.6B   ordinal           0.519    0.519       0.3450    0.3366     n.s.
embed-head 0.6B   nli               0.599    0.799       0.1005    0.1331     WORSE
Qwen3.5-2B        all six        worse everywhere                             WORSE x6
smart 27B         all six        better everywhere                            better x6
```

Three families where a 0.6B embedder beats the 4B: three wins. The family where it is much worse:
significantly worse. So the deployed "draft → verify → escalate" pattern works because the
verifier is *specialised*, not because verification beats self-confidence intrinsically — and
the pre-flight check is cheap: measure your candidate verifier's accuracy on the family first,
and never deploy one weaker than the thing it is verifying.

## What I did not measure

- **Jev.** Zero cloud calls. The reference arm is written (`jev_arm.py`, one `choice` question
  per item, same 1500-char cap, same bare option list) and has never been run. The sharpest
  single test, if it is ever taken: does Jev's calibration hold on `injection` and `langid`, the
  two cells where a transferred temperature fails significantly?
- **Speed.** CPU latencies of 220–340 ms/item under contention are not a speed claim and are not
  comparable to Jev's quoted 70–500 ms. A real number needs the concurrency sweep.
- **The `score` primitive.** Only `choice` and `noul` shapes here.
- Single seed, n=300 per cell. Bootstrap intervals cover test sampling noise only — temperatures
  are fitted once on calib and held fixed, so they are slightly optimistic. Said, not hidden.
- The cascade assumes the fallback's errors are what they are on exactly those items, which is
  measured honestly but does not generalise to a *different* fallback model.

---

**The one-line version:** constrained decoding is free, calibration is weak-but-real and worth
~0.01 Brier on an arm you would actually deploy, a deferral budget buys most of a frontier model
at a fifth of the calls but not all of it — and four tasks is not a benchmark. Measure AURC beside ECE or you will ship a model that is perfectly calibrated and
anti-correlated with being right.

The probability vectors behind every number here — seven arms, four suites, 2,000 items, frontier
model included — are packaged so you can test a calibration method against them without running
anything: `protoLabsAI/deferral-bench-v0`.
